# OA 权限体系面试问答

> 适用简历描述：主导万人级 OA 权限体系建设，基于 RBAC + 受限 ABAC + 对象级 ACL，实现多主体授权、角色继承、数据范围与对象级权限；设计三级权限加载路径及 JIT 四眼审批机制，稳态 L1 进程内判权 P99 达 1.25μs，正常运行条件下撤权 1 秒内生效。

## 使用说明

这份问答按当前项目的真实设计、代码和测试结果整理，用于统一面试口径。重点不是逐字背诵，而是理解以下主线：

1. RBAC 解决“能不能做”。
2. 受限 ABAC 解决“满足什么动态条件才能做”。
3. 数据范围和对象 ACL 解决“能操作哪些数据或对象”。
4. 权限快照和三级加载路径解决性能问题。
5. 数据库全局 epoch 和失效通知解决收权一致性问题。
6. JIT elevation-only 和四眼审批解决高危权限长期暴露问题。

任何题库都无法穷尽面试官的临场问题。回答时必须遵守本文最后的“口径红线”，不要把设计容量说成真实生产用户量，也不要扩大性能指标的适用范围。

Java 并发方向的延伸追问见 [`JAVA_ASYNC_CONCURRENCY_INTERVIEW_QA.md`](JAVA_ASYNC_CONCURRENCY_INTERVIEW_QA.md)，包括 `CompletableFuture`、线程池、JDK 21 虚拟线程、Spring 异步、Kafka Future 及相关选型边界。

## 一、开场标准答案

### 1. 请简单介绍一下这套权限体系

30 秒版本：

> 这套权限体系不是单纯的菜单 RBAC，而是分成四层。第一层用 RBAC 解决用户能不能执行某项操作，支持用户、组织、岗位、用户组四类主体以及角色继承；第二层用受限 ABAC，根据用户属性和接口参数进一步收窄；第三层用数据范围和对象 ACL 控制能看到哪些行、能操作哪些具体对象；第四层对高危权限增加 JIT 临时激活和四眼审批。
>
> 性能上，我把用户有效权限预计算成包含权限位图、数据范围、ABAC 来源和提权状态的快照，通过本地 Caffeine、Redis 和数据库重算三级加载路径读取。稳态 L1 命中的进程内判权 P99 是 1.25 微秒。收权通过数据库全局 epoch 失效，正常情况下各节点 1 秒内发现旧快照并重建。

90 秒版本：

> OA 的权限来源比较复杂：员工可能因为个人、部门、岗位或临时项目组获得角色；同一个角色还可能只允许查看本部门、下级部门或者指定区域；公文、知识库、文件等业务又存在所有者、共享人、参与人这类对象关系。所以只用传统 RBAC 容易出现角色爆炸，也解决不了 IDOR。
>
> 我的方案以 RBAC 为主干。授权关系是“主体—角色—权限”，角色继承通过闭包表预展开；数据范围附着在每条授权上，支持 ALL、ORG_AND_SUB、ORG、SELF、CUSTOM 和 NONE。ABAC 只做二次收窄，不负责产生基础权限，而且只允许读取用户属性和接口参数，禁止 Bean、类型、构造器和方法调用，求值异常默认拒绝。
>
> 判权时先从权限快照中用 RoaringBitmap 判断功能权限，再执行 ABAC；通过后把实际通过的角色来源放进调用上下文，数据权限层只合并这些来源的数据范围，避免一个未通过 ABAC 的宽权限角色把范围扩大。列表查询通过 MyBatis 拦截器改写 SQL，详情和写操作再做对象级校验，防止只保护列表却留下 IDOR。
>
> 缓存采用 L1 Caffeine、L2 Redis、L3 数据库重算。收权、角色变更和组织调整推进数据库全局 epoch，Redis Pub/Sub 只负责加速通知；各节点最多 1 秒重新读取 epoch。临时授权的有效时间还会压低快照 expireAt，防止授权已经过期但快照继续放行。

### 2. 白板上怎么画整体链路

```text
JWT / DEV 身份
  → @RequiresPerm 接口权限声明
  → RBAC 权限位图
  → 受限 ABAC 二次收窄
  → 高危权限 JIT 激活状态
  → AuthorizationContext 记录实际通过的权限和角色来源
  → @DataScope SQL 行级过滤 / 对象 ACL
  → @Sensitive 字段脱敏
```

## 二、业务背景与方案选型

### 3. 为什么不用纯 RBAC？

RBAC 适合表达“谁能做什么”，但不适合独立表达“能操作哪些数据”和“在什么条件下能做”。如果把华东经理、华南经理、不同金额审批人全部拆成角色，会造成角色爆炸。

因此由 RBAC 负责基础能力，数据范围负责组织维度，ABAC 负责金额、时间、请求参数等动态限制，对象 ACL 负责某一份公文、文件或知识文档的具体访问关系。

### 4. 为什么称为“RBAC + 受限 ABAC + 对象 ACL”？

RBAC 是主授权模型；ABAC 只能收窄已有 RBAC 权限，不能凭空授予权限；对象 ACL 解决某一业务对象的 OWNER、共享人、参与人等关系。

当前没有把通用关系图引擎放进实际判权链路，所以不能描述成完整 ReBAC。SpiceDB 只是预留适配，不是线上实际判权组件。

### 5. 你在项目里具体主导了什么？

> 我主要负责权限模型、授权语义、角色继承、权限快照、缓存失效协议、ABAC 安全边界、数据权限接入规范、JIT 审批以及对应的架构门禁和测试。实施时把工作拆成模型和写侧治理、读侧判权、业务数据接入、安全验证几个阶段，重点解决范围扩大、缓存陈旧和 IDOR。

### 6. “万人级”具体指什么？

> 这里指按万人规模的组织和权限数据进行设计和验收，不等同于声称线上已经有一万日活。主要体现在权限热路径不能查库、组织范围不能展开成几千个 IN 条件、角色继承需要预计算、快照按用户懒加载，以及全局失效后不能一次性重建全部用户。

如果没有真实万人生产数据，不能说“线上一万员工长期运行”或者编造峰值 QPS。

### 7. 为什么不把所有权限直接塞进 JWT？

JWT 中的权限在 Token 有效期内很难及时收回，而且数据范围、ABAC 来源、对象关系和临时提权状态变化频繁，不适合全部固化进 Token。JWT 主要承载可信身份，授权结果由服务端权限快照计算和失效。

### 8. 为什么不做一个远程 IAM 服务，每次请求都调用？

权限判断位于几乎所有受保护请求的热路径。逐次远程调用会增加延迟、网络抖动和故障面。当前方案让多个后端复用相同的安全契约和快照机制，在本地完成稳态判权；数据库和 Redis只在缓存失效或重建时参与。

## 三、RBAC、多主体授权和角色继承

### 9. 支持哪些授权主体？

支持四类主体：

- `USER`：直接给用户授权。
- `ORG_UNIT`：给组织授权，可选择是否向下级组织成员继承。
- `POSITION`：随员工有效岗位任职生效。
- `USER_GROUP`：面向跨组织项目组、委员会或临时协作组。

### 10. 为什么同时支持组织、岗位和用户组？

三者语义不同。组织表示行政归属；岗位表示职责；用户组表示跨组织协作关系。如果全部转换成人员逐个授权，维护成本高，而且员工调岗、退出项目组或离职时容易漏撤权。

### 11. USER_GROUP 与外部身份平台的 Group 是一回事吗？

不是。这里是 OA 自己管理的显式用户组，成员可以有独立有效时间窗，用于业务授权。不能把它说成 Casdoor 等身份平台组的直接映射。

### 12. `includeDescendants` 表示什么？

它控制授权主体是否覆盖下级组织成员，不等于数据范围。例如给“华东大区”授予角色并开启 `includeDescendants`，表示下属组织员工也能获得角色；这些员工能看本人、本部门还是整个华东，由 `scopeType` 和 CUSTOM 范围决定。

### 13. 数据范围有哪些类型？

- `ALL`：全部数据。
- `ORG_AND_SUB`：本人有效任职组织及下级组织。
- `ORG`：本人所在组织。
- `SELF`：本人数据。
- `CUSTOM`：指定组织或组织子树。
- `NONE`：只有功能权限，不贡献业务数据范围。

### 14. 为什么数据范围放在授权记录上，而不是只放角色上？

同一个角色授给不同主体时，实际范围可能不同。例如“部门经理”授给研发经理时锚定研发部门，授给财务经理时锚定财务部门。角色上保留默认或最大可分配范围，实际范围放在授权记录上，更符合业务语义。

### 15. 多条授权的数据范围如何合并？

授权关系是加法语义，因此同一个权限通过多个有效来源获得时，数据范围做并集。但必须先经过 ABAC，只合并本次真正通过 ABAC 的角色来源；不能让 ABAC 失败的 ALL 来源扩大另一个 CUSTOM 来源。

### 16. 角色继承如何实现？

写侧保存直接继承边，修改时用递归 CTE 检测环路，再重建传递闭包表。读侧直接查询闭包，不在每次判权或快照重建时递归遍历角色图。

当前继承方向是“父角色继承子角色权限”。例如闭包中的 `SUPER_ADMIN → HR_ADMIN` 表示 SUPER_ADMIN 包含 HR_ADMIN 的权限。

### 17. 为什么既有直接边表又有闭包表？

直接边表保存管理员真正配置的关系，便于编辑、展示和解释；闭包表保存传递结果，供读侧快速查询。这是将复杂度放在低频写侧、让高频读侧保持简单的设计。

### 18. 如何避免继承成环？

更新继承关系时先获取租户级数据库事务锁，写入候选直接边，再使用递归 CTE 检查是否存在 `ancestor = descendant`。发现环路抛出冲突异常，整个事务回滚；通过后再重建闭包并推进全局 epoch。

### 19. 并发修改继承关系怎么办？

使用 PostgreSQL advisory transaction lock 将同一租户的角色图修改串行化，避免两个请求单独看都不成环、合并后却成环。角色记录还有 version 乐观锁，用于防止普通编辑覆盖。

### 20. 角色停用后，已有授权如何处理？

停用角色后推进全局 epoch，旧快照失效。闭包和权限查询只消费 ACTIVE 角色，所以重新计算后该角色不再提供权限；授权服务也禁止对非 ACTIVE 角色新增授权。

### 21. 为什么不能随便删除角色？

删除会影响历史审计和授权来源解释。内置角色不能删除；已有授权记录引用的角色也不能直接删除；普通未使用角色采用软删除，并清理继承关系、重建闭包。

### 22. 重复授权如何保证幂等？

根据租户、主体、角色、范围、授权类型和有效期生成业务锁键，获取事务 advisory lock 后查询相同的有效授权。存在时直接返回原授权 ID，避免两个并发请求创建重复授权。

### 23. 如何防止管理员给自己加权？

授权服务端会拒绝操作者直接给自己新增角色。对于内置角色或直接、继承包含权限治理能力的高权角色，还要求操作者具有 IAM 管理权限，不能只根据角色名称判断是否高权。

## 四、受限 ABAC

### 24. ABAC 主要解决什么问题？

解决 RBAC 和组织范围不适合表达的动态限制，例如审批金额不能超过阈值、只能在特定时段操作、请求参数必须属于某种业务类型。

“华东经理只能查看华东数据”应优先使用 CUSTOM 数据范围；只有金额、时间、参数等条件才使用 ABAC。

### 25. 为什么 ABAC 只能收窄，不能直接授权？

如果 ABAC 可以独立产生权限，会绕过角色生命周期、授权审批和来源解释。系统先确认用户通过 RBAC 持有权限，再检查属性条件；ABAC 条件永远不能凭空产生 permission bit。

### 26. ABAC 条件如何组合？

同一个角色、同一个权限下的多条条件是 AND；不同授权角色来源之间是 OR。一个角色分支必须满足该分支全部约束，但用户只要存在一个合法来源分支通过即可。

### 27. 某个来源没有 ABAC 条件怎么办？

该来源视为无条件分支。只要这个来源合法持有权限就可以通过，不能因为用户的其他来源配置了限制而反过来限制无条件来源。

### 28. 为什么不用完整 SpEL？

完整 SpEL 可以访问类型、Bean、构造器和方法调用，配置人员可能借此访问系统能力。实现使用只读求值上下文，只暴露受控的 `user`、`args`、`p0`、`a0` 和方法参数；限制表达式长度，并禁止 `T()`、`new`、Bean 引用、方法调用、赋值、Class、Runtime、System 和集合执行语法。

### 29. ABAC 求值异常怎么办？

按拒绝处理，也就是 fail-closed，同时记录错误指标和日志。权限表达式写错不能成为默认放行的理由。

### 30. ABAC 会不会拖慢热路径？

条件随权限快照加载，表达式编译结果放在本地缓存，运行时只读取用户上下文和方法参数，不查数据库、不调用远程服务。但 ABAC 仍比单纯位图判断更重，所以只应用于确实需要动态条件的权限点。

### 31. 为什么 ABAC 决策需要返回通过的角色 ID？

数据范围属于具体授权来源。如果 ABAC 只返回 boolean，后续不知道应该合并哪些 scope。实际决策返回“是否允许 + 通过的角色集合”，数据权限层再从这些通过来源计算有效范围。

### 32. ABAC 开关关闭后是什么行为？

关闭时保持纯 RBAC 兼容行为。ABAC 模式会写入权限快照，读取 L1/L2 时也会校验模式，避免把另一种模式下构建的快照错误复用。

## 五、接口权限、数据权限和对象 ACL

### 33. 接口权限和数据权限有什么区别？

接口权限回答“能不能调用员工查询接口”，数据权限回答“调用后能看到哪些员工”。只有接口权限没有数据权限，部门经理可能获取全公司员工；只有数据权限没有接口权限，安全入口又难以治理。

### 34. 数据范围如何落到 SQL？

业务方法使用 `@DataScope` 声明权限码、目标表、别名和组织、路径、用户字段。切面从权限上下文取当前权限对应的范围，MyBatis 拦截器将其翻译成 WHERE 条件：

```sql
ALL          → 不追加条件，但记录已经明确求值
NONE         → 1 = 0
SELF         → owner_id = 当前用户
ORG          → org_id IN (...)
ORG_AND_SUB  → org_path LIKE '/1/23/%'
CUSTOM       → 指定组织、路径前缀和本人条件的并集
```

### 35. 为什么组织子树使用路径前缀，不展开所有部门 ID？

万人组织下，一个节点可能有几千个后代。展开成巨大 IN 列表会增加 SQL 长度、网络传输和解析成本，也容易破坏执行计划。使用物化路径和前缀索引后，子树范围可以转换成稳定的 `LIKE 'path/%'` 前缀条件。

### 36. SQL 改写失败如何处理？

默认拒绝执行。权限没有通过接口判权、目标表未被实际查询、表别名错配、路径或 SQL 条件解析失败、受管表没有数据权限上下文等情况，都不能静默放行。

### 37. 为什么 DataScope 只能使用本次实际通过的接口权限？

防止业务方法随意声明一个范围更大的权限。例如接口只通过了 limited 权限，内部却读取 admin 权限的 ALL 范围。AuthorizationContext 会记录本次真正通过的权限，DataScope 只能消费其中的权限。

### 38. 列表已经过滤，详情接口还会有风险吗？

会。攻击者可以跳过列表，直接修改 URL 中的对象 ID，请求其他部门的数据，这是典型 IDOR。因此详情、更新、删除等按 ID 的路径，在操作前都要加载目标对象的组织、所有者或 ACL 信息，再做对象级访问检查；更新和删除 SQL 最好再次带 owner、tenant 等条件。

### 39. 对象 ACL 如何实现？

根据对象选择策略：文件使用 OWNER；知识文档使用 OWNER 加共享 ACL；公告使用发布时受众快照；流程单据使用申请人、当前处理人、参与人和有效委托关系。

`@ObjectScope` 用于声明入口策略、原因和受影响表，并纳入架构门禁；真正的 OWNER、ACL 或参与者谓词仍由服务或 SQL 执行。

### 40. 为什么不把所有对象关系都放进一张通用 ACL 表？

通用 ACL 表适合共享关系稳定的对象，但有些权限来自实时业务状态，例如流程当前处理人、会议参与人、公告发布时受众。强行全部同步到一张 ACL 表会产生双写和一致性问题。因此统一安全协议和测试要求，具体对象谓词允许由业务模型实现。

### 41. 字段权限如何处理？

行级权限决定能否看到记录，字段权限决定敏感字段如何展示。敏感数据在存储层加密，在序列化层根据 FIELD 权限决定明文、掩码或隐藏。前端隐藏字段不属于安全控制，后端响应必须已经完成脱敏。

### 42. 数据权限是否已经覆盖所有业务表？

> 权限协议、架构门禁和主要业务路径已经接入，但不能声称所有历史 SQL 天然自动安全。对象谓词仍需要业务方法实现，新接入路径通过 Golden 和架构测试登记，防止新增裸访问。当前完成的是主要业务对象迁移，不是数据库 RLS 对全库无条件兜底。

## 六、权限快照和三级加载路径

### 43. 所谓“三级缓存”具体是什么？

更严谨地说是三级权限加载路径：L1 是进程内 Caffeine 快照，L2 是 Redis 快照，L3 是从数据库重新计算。L3 严格来说不属于缓存，而是真值回源。

### 44. 权限快照包含什么？

包括全局 epoch、用户版本、权限位图、高危权限激活位、按权限和角色来源的数据范围、ABAC 分支、委托人、构建时间和 expireAt。

### 45. 权限快照如何构建？

构建时先读全局 epoch 和用户版本，再获取用户有效任职、组织祖先、岗位、有效用户组、有效授权、角色继承权限、ABAC 条件、委托和最近时间边界，最后生成不可变快照。

版本必须先于业务数据读取，避免先读到旧数据、后读到新版本，却把旧数据错误标记为新版本快照。

### 46. 为什么使用 RoaringBitmap？

权限 ID 映射为整数后，判断权限变成位图 contains；权限集合并集、序列化和内存占用也比字符串集合更稳定。字符串权限码只在入口经权限目录映射成整数 ID，热路径不做数据库查询和复杂对象遍历。

### 47. L1 和 L2 的默认参数是什么？

L1 默认最大 2 万用户快照，写入后 TTL 5 分钟；L2 Redis 默认最长 30 分钟。但临时授权或组成员关系有更早时间边界时，两层缓存的有效期都会被快照 expireAt 提前截断。

### 48. 为什么 L2 TTL 比 L1 长？

L1 追求进程内高命中和受控内存；L2 用于减少节点重启或 L1 淘汰后的数据库重算。即使 L2 存得更久，读取时仍然校验 epoch、ABAC 模式和 expireAt，不能拿到就直接相信。

### 49. L1、L2、L3 的大致性能分别是多少？

L1 命中是微秒级；L2 通常是毫秒级；数据库完整重算大约十几到几十毫秒，取决于授权数量、组织关系和数据库状态。`1.25μs` 只代表稳态 L1 进程内权限判断，不能代表冷缓存或完整 API。

### 50. Redis 故障怎么办？

L1 命中不受影响；L1 未命中时读取 Redis 失败会降级到数据库重算，写 Redis 失败也不会阻塞业务。Redis不是真值，因此不会因为 Redis 中存在快照就跳过 epoch 校验。

### 51. 数据库故障怎么办？

已有有效 L1 快照可以短时间继续工作，但冷用户或需要重建的快照无法安全计算时应失败，不能构造一个放行结果。高危权限和失效后的请求以 fail-closed 为原则。

### 52. 全局 epoch 会不会造成缓存雪崩？

存在集中重建风险，因此全局失效只用于安全敏感且低频的收权事件，而且不是立即重建一万用户，而是按下一次访问懒加载。当前主要依靠低频写、懒加载和 L1/L2 分层缓冲；继续扩大并发时，应增加按用户 single-flight、重建并发限流和热点用户预热。不能声称这些后续优化已经全部实现。

### 53. 如何发现缓存与数据库真值不一致？

系统提供 explain 接口比较缓存快照和数据库重算结果，并对少量请求执行异步影子校验，记录 mismatch 指标。影子校验使用独立线程和有界队列，队列满时允许丢弃诊断任务，不能反过来拖慢业务请求。

## 七、缓存失效和撤权一致性

### 54. 撤权为什么能在 1 秒内生效？

撤权事务推进数据库中的全局 epoch，并清理本节点缓存、发送 Redis 失效通知。其他节点收到通知会立即清理；即使通知丢失，也会最多每 1 秒重新读取数据库 epoch，发现快照版本落后后拒绝使用并重建。

这个口径的前提是数据库和应用节点正常可达。1 秒是缓存收敛上界，不是数据库事务耗时。

### 55. 为什么 epoch 放在数据库，而不是只放 Redis？

Redis 可能重启、被清空或丢失数据。如果 Redis 是唯一版本真值，epoch 归零后旧快照可能被误认为有效。因此数据库 epoch 是持久化真值，Redis Pub/Sub 只是低延迟通知通道。

### 56. 为什么授权和撤权使用不对称失效策略？

收权晚生效是安全问题，因此撤销、角色权限收缩、调岗和组织变化统一推进全局 epoch。给某个用户新增权限，只 bump 用户版本、删除该用户 L1/L2 并广播个人失效；通知丢失最坏是新权限晚生效，不会造成越权。

### 57. 为什么不在每次判权时查询用户版本？

如果每次都查数据库或 Redis，L1 缓存就失去意义。当前热路径只比较本地最多缓存 1 秒的全局 epoch；个人加权通过主动删除和通知传播，安全敏感的个人收权仍统一推进全局 epoch。

### 58. 临时授权到期为什么不依赖定时任务？

快照 expireAt 取默认 TTL 与最近授权、用户组成员时间边界的最小值。到达有效期后，即使缓存对象仍存在，也会被判定过期并重建。定时任务只负责把过期记录正式标记为撤销并补充审计。

### 59. 调岗为什么也要失效权限？

数据范围锚定在员工有效任职组织上。调岗修改的是任职关系而不是组织树，如果只监听组织树变化，员工可能继续使用旧部门范围。因此主岗、兼岗变化和范围收缩都要推进可靠失效。

### 60. 离职为什么不能只清缓存？

数据库授权仍然存在时，账号重新启用或身份重新关联后权限可能复活。因此离职既要失效快照，也要撤销或冻结持久化授权关系。

## 八、性能指标

### 61. P99 1.25μs 是怎么测出来的？

通过服务端 benchmark 接口，先执行约 2000 次预热，让快照进入 L1 并完成 JVM JIT 编译，再连续执行约 2 万次 `engine.has(userId, permCode)`，记录纳秒耗时、排序并计算分位数。

测量对象是稳态、L1 命中、进程内单次权限判断，不包含 HTTP、JSON、网络、数据库和业务 SQL。

### 62. 为什么可以做到微秒级？

热路径主要是权限码到整数 ID 的内存映射、一次 Caffeine 获取、epoch 本地值比较、expireAt 比较和位图 contains，没有数据库查询、Redis 请求和组织树递归。

### 63. 这是不是严格的通用性能基准？

不是。它属于项目验收级微基准，不能跨机器泛化。更严格的测试应使用 JMH，控制预热、CPU 频率、GC、线程数和逃逸优化，并补充并发、L2 命中和 L3 重建场景。因此只能说“当前环境稳态判权 P99 1.25μs”。

### 64. 1.25μs 是否包含 ABAC？

主要代表稳态基础权限热路径。复杂 ABAC 表达式需要单独统计，不能把位图判权数据直接当成所有 ABAC 请求的耗时。

### 65. 遇到过什么性能问题？

最初影子校验在请求线程同步执行，1% 采样会触发一次约 5ms 的数据库完整重算，刚好把 P99 顶到约 5ms。后来改成独立线程、有界队列和丢弃策略，P99 回到约 1.25μs。这个问题说明可观测性代码也必须计入热路径预算。

## 九、JIT 临时提权和四眼审批

### 66. JIT 和普通临时授权有什么区别？

普通临时授权表示在时间窗内真正获得一个角色及其数据范围。JIT 是 elevation-only，只临时激活用户已经长期持有角色中的高危权限位，不产生新的 RBAC 角色、ABAC 来源或数据范围。

### 67. 为什么 JIT 只能激活已持有角色？

否则用户只要能调用提权接口，就能申请任意角色，等于自助越权。它类似 sudo：只有已经处于授权范围中的能力，才允许临时激活。

### 68. 为什么永久持有权限还要 JIT？

某些低频高风险操作不适合长期处于激活状态，例如敏感数据批量导出、组织删除或权限治理。长期角色定义“最多能做什么”，JIT 决定“此刻是否允许启用高危位”。

### 69. 四眼审批如何实现？

申请时只创建 PENDING 记录，不立即生成权限。另一名拥有审批权限的用户批准后，才生成 elevation-only 临时授权；申请人与审批人不能相同。

审批决策使用 `SELECT FOR UPDATE` 锁定申请，UPDATE 只允许从 PENDING 转换，防止两个审批人并发重复处理。

### 70. 审批时为什么还要重新检查角色？

审批等待期间，角色可能被停用，申请人的长期角色也可能被撤销。因此批准时重新检查目标角色仍为 ACTIVE，并确认申请人仍持有对应的直接永久角色，不能只相信申请创建时的状态。

### 71. JIT 会不会扩大长期数据范围？

不会。JIT 临时记录的 scope 固定为 NONE，只写高危权限激活位，不进入 RBAC、ABAC 和数据范围合并。

这是权限加固中修复过的关键问题：如果将 JIT 当作 scope=ALL 的普通临时角色授权，会把长期 CUSTOM、ORG 或 SELF 范围静默扩大为全公司。

### 72. JIT 最长多久？

默认最长 8 小时，申请必须填写理由。快照 expireAt 会被提权到期时间截断，因此不依赖定时任务才能终止权限。

### 73. 重复申请怎么办？

同一租户、申请人和角色只允许一条 PENDING 申请，数据库有部分唯一索引；插入时使用冲突忽略并返回已有申请 ID，保证并发重试幂等。

### 74. 当前是否已经接入 BPMN 工作流？

> 当前使用 IAM 模块内部审批表，没有反向依赖 flow 模块，主要是为了避免 IAM 和流程模块形成循环依赖。通过 approvalInstanceId 保留审批关联，未来可以通过事件或独立接口接外部 BPM 编排。

不能说已经上线完整的 BPMN 提权流程。

### 75. 临时提权能覆盖长期授权吗？

不能。JIT 只能激活长期角色已有的高危位，并且不改变长期授权的数据范围。长期角色被撤销后，等待中的申请无法批准；旧快照通过全局 epoch 失效。

## 十、多服务、安全边界和测试

### 76. 怎么防止开发人员忘记写权限注解？

构建阶段扫描 Controller，要求每个接口必须明确声明 `@RequiresPerm` 或 `@PublicApi`；运行时还有 fail-closed 拦截器，没有声明授权立场的业务 Handler 直接返回 403。`@PublicApi` 要求写明公开原因，避免为了通过测试而随手标记公开。

### 77. 前端隐藏按钮算权限控制吗？

不算。前端权限只改善用户体验，包括路由、菜单、按钮展示和权限版本刷新。攻击者可以绕过前端直接调用 API，后端接口判权、数据范围和对象校验才是真正安全边界。

### 78. 多服务如何保持权限一致？

多个后端复用统一的安全注解、权限检查接口和快照协议；API Golden 固定“接口—权限码”关系，架构测试检查未声明接口、数据访问旁路和对象权限登记。

这不是每个请求都远程调用一个 IAM 服务，而是让各服务遵循相同安全契约和失效协议，避免网络调用进入判权热路径。

### 79. 如何测试 IDOR？

使用两个不同组织或对象关系的账号：账号 A 通过列表看到自己的对象，然后拿账号 B 的对象 ID 直接请求详情、更新、删除和状态变更，预期全部拒绝。还需要覆盖猜 ID、批量接口、导出、附件下载和预签名地址，不能只验证“列表看不到”。

### 80. 有哪些工程门禁？

包括 Controller 权限覆盖扫描、API Golden、数据访问 Golden、JDBC bypass 架构测试、角色继承环路、ABAC 来源范围、JIT 自批和并发审批、缓存收权、对象 ACL、详情和写操作 IDOR。

当前项目验证中，IAM 有 55 个测试，前端有 109 个测试，并执行了后端聚合构建、前端生产构建和运行态冒烟。数字会随项目演进变化，面试前应以当前报告为准。

### 81. 权限审计记录什么？

至少记录操作者、目标主体、角色或权限、授权范围、有效期、理由、结果和关联审批 ID。高危操作和提权态操作单独标记，便于追溯谁在什么时间、因为什么原因获得并使用了权限。

### 82. 为什么禁止业务直接写授权表？

权限写操作不只是修改一张表，还必须推进版本、清缓存、广播失效并记录审计。直接 SQL 修改授权记录会绕过失效协议，让旧快照继续放行。所有授权、撤权和角色修改必须经过统一写侧服务。

## 十一、难点、缺陷与复盘

### 83. 这个项目最难的点是什么？

> 最难的不是判断一个 permission code，而是保持权限来源、ABAC 条件和数据范围三者的一致性。一个用户可能通过多个角色持有同一个权限，如果只得到一个 boolean，后续容易把失败来源的宽范围也合并进来。最终让 ABAC 返回实际通过的角色来源，并在请求上下文保存这些来源，数据权限只消费通过来源，解决了组合越权问题。

### 84. 遇到过最严重的权限问题是什么？

> JIT 最初如果按普通临时角色授权处理，可能把长期 CUSTOM 或 SELF 范围扩大为 ALL。后来将其改为 elevation-only：只增加高危位，scope 固定 NONE，不进入 RBAC、ABAC 和 scope 合并。这类问题只测“能不能调用接口”发现不了，还必须同时断言权限位和数据范围没有变化。

### 85. 还踩过哪些坑？

可以根据面试时间选择两到三个展开：

- 调岗改变任职关系而不是组织树，只监听组织树会让旧部门范围继续生效。
- 同步影子校验查库将判权 P99 顶到约 5ms。
- 启动管理员初始化写入授权后只改数据库 epoch，没有清本地空快照，导致短暂 403。
- 列表受到保护，但详情和写操作没有目标对象检查，形成 IDOR。
- ABAC 只返回 boolean，导致失败角色来源的宽范围被错误合并。
- 裸 SQL 修改授权记录绕过 epoch 和失效通知，导致旧快照继续使用。

### 86. 当前方案有哪些不足？

> 第一，当前产品仍按单租户运行，虽然关键查询带 tenantId，但不能宣传成完整多租户隔离，也没有启用数据库 RLS。第二，角色 defaultScope 同时承担默认范围和最大可分配范围，不能表达“默认 SELF、最多 ORG”。第三，全局 epoch 后的同用户并发重建还可以增加 single-flight。第四，微秒指标是稳态微基准，不是完整 API 压测结果。

### 87. 如果重新设计，会改什么？

> 我会拆分角色的 defaultScope 和 maxAssignableScope；给快照重建增加按用户 single-flight 和并发限流；补充 JMH、多节点失效故障注入和缓存雪崩测试；真正启用多租户时增加 TenantLine 或数据库 RLS 作为纵深防御；JIT 审批则通过事件或独立审批接口接外部 BPM，避免模块循环依赖。

## 十三、口径红线

面试中以下内容不能说错：

- 不说“接口 P99 1.25μs”，应说“预热后、L1 命中的进程内判权 P99”。
- 不说“Redis 保证撤权 1 秒生效”，数据库全局 epoch 才是真值。
- 不说“任何故障下绝对 1 秒”，该上界需要数据库和应用节点正常可达。
- 不说“完整 ReBAC”，当前实现是对象 ACL。
- 不说“完整多租户”，当前产品按单租户运行。
- 不说“ABAC 可以产生权限”，它只能收窄 RBAC。
- 不说“JIT 临时获得新角色”，它只激活已有长期角色的高危权限位。
- 不说“JIT 已接 BPMN 工作流”，当前是 IAM 本地四眼审批表。
- 不说“所有业务表自动具备行级权限”，业务接入仍需注解、受管 Mapper 或对象谓词。
- 不说“前端隐藏按钮就是权限控制”。
- 不把 L3 数据库重算严格称为缓存；受到质疑时改称三级加载路径。
- 没有真实万人线上经历时，不说“线上服务一万用户”，只说“按万人规模设计和验收”。
- 不把当前环境的微基准结果说成跨机器、跨并发场景的固定结果。

## 十四、面试前最低复习清单

面试前至少做到：

1. 能不看稿讲出 30 秒和 90 秒版本。
2. 能画出完整判权链路。
3. 能解释角色继承闭包表和环路检测。
4. 能解释 ABAC 为什么返回通过的角色来源。
5. 能写出六种数据范围对应的 SQL 思路。
6. 能解释列表权限与 IDOR 的区别。
7. 能讲清 L1、L2、L3、epoch、userVersion 和 expireAt。
8. 能说明 1.25μs 的测量边界。
9. 能说明 JIT 为什么是 elevation-only。
10. 能主动承认单租户、非完整 ReBAC、非全库 RLS 等现有限制。
