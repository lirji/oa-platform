## 实现期新增的决策

### ADR-0012 · 收权走全局纪元，授权走个人版本（**刻意不对称**）

- **收权**（撤销、部门级授权变更、角色权限变更、组织调整、离职）→ 推进**全局纪元**，
  各节点 1 秒内全量作废快照。
- **给个人加权** → 只推进他自己的版本号 + 本节点剔除 + 通知其它节点。

**理由**：撤权延迟生效是安全事故，值得付出一次全量重算；而新权限晚几分钟生效不构成安全问题。
放弃对称换来的是热路径只需比对一个每秒刷新的纪元，不必为每个请求查一次用户版本 ——
**这是判权 P99 能压到 1 μs 的关键**。

**否掉的方案**：每次判权都校验用户版本（每请求多一次 DB 读，热路径不可接受）；
部门级授权时逐个 bump 受影响用户（可能几千人，既慢又容易漏）。

### ADR-0013 · 兜底方案由「URL 映射表」改为「fail-closed 拦截器」

计划里原写"用 URL 映射表做兜底过滤器"。实现时改成
**没有授权注解的 handler 一律拒绝**。

**理由**：URL 表需要人维护，漏配一条就漏一个接口；而 fail-closed 覆盖**全部**未来新增的接口，
不需要任何人记得做什么。它与构建期的 `ControllerPermissionCoverageTest` 是双保险，
正常情况下永远不会触发。

### ADR-0014 · JIT 提权只能激活「已持有」的角色

**理由**：这正是 JIT 提权的原义 —— 平时有这个角色但处于未激活态，做高危操作时才临时点亮。
就像 sudo：不在 sudoers 里的人，能执行 sudo 命令也没用。
少了这条约束，"自助提权"就等于"自助越权"。

**推论**：提权接口的**权限点可以放开给普通员工**，因为真正的闸门在服务层而不在接口权限上。
同理，委托代理也应该是员工自助能力，而不是管理员权限。

### ADR-0015 · 单据的 `org_path` 是发生时快照，组织调整不回刷

**理由**：这既是性能优化（数据权限免 join），也是正确的业务语义 ——
"这张请假单属于当时的那个部门"。

**但任职关系的 `org_path` 要跟随组织移动**：那是当前的结构性事实，不是历史凭证。
两者的区别写在 `V3__org_directory.sql` 里。

### ADR-0016 · Flyway 开 `out-of-order`

按模块划分迁移版本号区间（V1 app / V2-9 org / V10-19 iam / V20-29 flow / V30-39 attendance）
必然产生"后补的 V4 排在已执行的 V10 之前"。

**接受它的前提**：各模块拥有互不相交的 schema，跨模块迁移之间没有顺序依赖，
乱序执行不会产生错误结果。若将来出现跨模块顺序依赖，
应改用**时间戳版本号**而不是继续开这个开关。

### ADR-0017 · jsonb 列用 TypeHandler，不用 `stringtype=unspecified`

PG 不会把 varchar 隐式转成 jsonb。两种解法：
在 JDBC URL 上加 `?stringtype=unspecified` 让 PG 自己推断，或用 TypeHandler 精准处理。

**选后者**：前者会放松**所有**字符串参数的类型推断，等于用全局的类型宽松换局部的方便。
代价是每个 jsonb 字段要显式标注 —— 显式是对的，"这一列是 jsonb"本来就该被看见。

### ADR-0018 · 缓存加载必须 get-then-put，不能用 `cache.get(key, loader)`

`Caffeine.get(key, mappingFunction)` 底层是 `ConcurrentHashMap.computeIfAbsent`，
持有 bin 上的 `synchronized` 锁执行 mappingFunction。
**JDK21 的虚拟线程一旦在 `synchronized` 里阻塞（这里是 JDBC 查询）就会 pin 住载体线程。**

实测后果：加了员工读缓存后吞吐从 555 QPS **塌到 17 QPS** —— 加缓存比不加慢 30 倍。

**改用 get-then-put**（`getIfPresent` → 加载 → `put`），加载过程完全不持锁。
代价是同一 key 可能被并发重复加载，对"每人一个 key"的访问模式几乎不会发生。

**推论（已写进 CLAUDE.md）**：新引入任何**在 `synchronized` 块里做 I/O** 的组件，
都要重跑 Phase 0 的 pinning 探针。Phase 0 的结论只覆盖了当时的组件。

### ADR-0019 · Docker 镜像不做容器内构建

本项目依赖的中台制品装在宿主机的 system maven 仓库，容器里看不到。
要么把整个仓库挂进去，要么把中台源码也搬进构建上下文 —— 两条路都比
"先在宿主机构建、镜像只装 jar"更脏。构建入口统一走 `deploy/build-images.sh`。
